Post-Quantum TLS Migration Readiness

Hybrid X25519MLKEM768 key exchange in TLS 1.3: group-list behaviour, HelloRetryRequest, and measured results. The headline result: on OpenSSL, a flat server group list silently lets the client’s order decide — a client that supports the hybrid but defers its keyshare lands on classical X25519 with no error and no HelloRetryRequest. The tuple group list (X25519MLKEM768/X25519) fixes it. Everything below is labelled by how it was established, and every measured claim points at a runnable test and its unedited output.

F-1 · HIGH measured

Flat server group list ignores server preference — deferred hybrid keyshare silently falls back to classical X25519

With a flat server list, the negotiated group follows the client’s order in both directions (cases D5 / D5b). A client that supports X25519MLKEM768 but predicts only a classical keyshare completes the handshake with classical X25519 — no error, no HelloRetryRequest (case R2). With the tuple list, the server sends a HelloRetryRequest and the client negotiates the hybrid (case R1). This is the same downgrade class as CVE-2026-2673 but is not a reproduction of it: that CVE is specifically about the DEFAULT keyword (affects 3.5.0–3.5.5 / 3.6.0–3.6.1, fixed in 3.5.6 / 3.6.2, CVSS 6.5), and the build measured here is 3.5.9. F-1 is the residual flat-list behaviour.

Full remediation in the configuration guide; proof in the regression check (R1/R2/R3, 9/9 PASS) and the unedited operator-check output below.

How to read this matrix

  • “Yes” for a hybrid group means the stack can negotiate X25519MLKEM768. It does not mean your deployment does: the negotiated group is what matters, and a flat-list OpenSSL server (F-1) or a legacy peer can silently land on classical X25519. Run operator_check.py against your own server to find out what it actually negotiates.
  • Standalone ML-KEM is the least portable option. Only OpenSSL 3.5.9 (measured) and BoringSSL for ML-KEM-1024 (specification-derived) support it; wolfSSL and Go do not. Use the hybrid group for interop.
  • Group-preference enforcement is the dimension most likely to surprise you. OpenSSL’s flat list does not enforce server preference (F-1); the tuple list does. For BoringSSL this dimension is unverified here — do not assume it behaves like OpenSSL.
  • TLS 1.2 is classical-only everywhere. There is no post-quantum key exchange in TLS 1.2 (RFC 10024 defines the hybrid groups for TLS 1.3 only). Any deployment that still allows TLS 1.2 allows classical-only key exchange.

03Configuration guide — enforcing the hybrid on OpenSSL and wolfSSL

Copy-paste server settings for the F-1 remediation, the HelloRetryRequest behaviour to expect, the misconfigurations to avoid, and a runnable test for every claim. Commands were run against OpenSSL 3.5.9 and wolfSSL 5.9.4-stable built from source; exact outputs are in the evidence pack.

1. OpenSSL 3.5.9 — use the tuple syntax

# Server: put the hybrid in its own, most-preferred tuple.
openssl s_server -accept 443 -cert server.crt -key server.key \
    -tls1_3 -groups "X25519MLKEM768/X25519" -CAfile ca.crt

The / separates tuples of comparable security. X25519MLKEM768 alone in the first tuple means “prefer the hybrid over everything in a later tuple”. The classical X25519 in the second tuple remains available as a fallback for clients that cannot do the hybrid at all. (OpenSSL 3.5+ syntax; see SSL_CTX_set1_curves(3SSL) — “Group tuples of comparable security are defined by separating them from each other by a tuple separator /.”)

What to expect measured

A client that supports the hybrid but predicts only a classical keyshare gets a HelloRetryRequest instead of a silent classical fallback. The HRR is an 88-byte ServerHello carrying the RFC 8446 magic random cf21ad74e59a6111be1d8c021e65b891c2a211167abb8c5e079e09e2c8a8339c and a key_share request for group 0x11ec. The client then retries with a hybrid keyshare and the negotiated group is X25519MLKEM768. Verified live (R1 in regression_hrr.py, 9/9 PASS; raw log hrr_R1_tuple_hrr_client.log in the pack): 

<<< TLS 1.3, Handshake [length 0058], ServerHello
    02 00 00 54 03 03 cf 21 ad 74 e5 9a 61 11 be 1d
    03 04 00 33 00 02 11 ec

2. wolfSSL 5.9.4 — hybrid via --pqc, with two caveats

# Server: hybrid group, and -C high enough to serve more than one connection.
./build/examples/server/server -p 443 -v 4 -c server.crt -k server.key \
    -A ca.crt -d --pqc X25519MLKEM768 -C 100

The example server takes a single --pqc value. It does not expose a group list or a tuple syntax, so the OpenSSL-style preference test does not apply to it — see the matrix.

Caveats measured

  • Standalone ML-KEM is not supported. --pqc ML_KEM_768 makes the server refuse to start: “invalid post-quantum KEM specified” (server.c:853). Use the hybrid group for interop (F-2).
  • One connection by default. The example server serves exactly 1 connection unless -C <num> is given (F-7). Set -C 100 or higher.
  • Do not health-check it with a bare TCP connect. A probe connection makes SSL_accept fail with SOCKET_ERROR_E (-308) and the server exits (F-7). Check readiness with ss -ltn instead.
  • Client exit behaviour. The example client waits for the server’s application reply after the handshake; use benchmark mode -b 1 so it exits cleanly and prints wolfSSL_connect avg took: X milliseconds.

Runnable test for this claim

The same operator_check.py works against a wolfSSL server (it only needs an OpenSSL 3.5+ s_client on the operator’s side). Expected: test B passes (the server supports the hybrid). Test A depends on the wolfSSL server’s group handling, which the example server does not expose as a list — treat test A against wolfSSL as informational, not as a pass/fail on the tuple remediation (which is OpenSSL-specific).

3. Verifying the negotiated group (both stacks)

# One-off check with s_client (OpenSSL 3.5+):
openssl s_client -connect <host>:443 -tls1_3 -groups X25519MLKEM768 \
    -CAfile ca.crt -brief
# Look for: "Negotiated TLS1.3 group: X25519MLKEM768"

# Deferred-keyshare check (the F-1 test):
openssl s_client -connect <host>:443 -tls1_3 \
    -groups "*X25519:X25519MLKEM768" -CAfile ca.crt -brief -msg
# Correctly configured server: an 88-byte ServerHello (HRR) appears first,
# then the negotiated group is X25519MLKEM768.
# Misconfigured (flat-list) server: no HRR, "Peer Temp Key: X25519".

Run operator_check.py against your server for the full check. Correct output is ALL PASS (exit 0). If test A fails while test B passes, your server supports the hybrid but does not enforce it — apply the tuple-syntax setting in §1 (OpenSSL) or check your stack’s equivalent. If both fail, the server does not support the hybrid at all — upgrade the TLS library (OpenSSL 3.5+, wolfSSL with WOLFSSL_MLKEM + WOLFSSL_PQC_HYBRIDS, BoringSSL, or Go 1.24+).

Full source — operator_check.py (the script that produced the output above) 
#!/usr/bin/env python3
"""Operator check: does my TLS server negotiate the hybrid group when a
client defers the hybrid keyshare?

This is the single-script regression check for finding F-1 (flat server
group list ignores server preference; a client that defers the hybrid
keyshare silently falls back to classical X25519). Point it at any TLS 1.3
server and it tells you whether that server enforces the hybrid.

Usage:
    python3 operator_check.py --host example.com --port 443
    python3 operator_check.py --host 127.0.0.1 --port 8443 --openssl /path/to/openssl
    python3 operator_check.py --host example.com --port 443 --cafile /path/to/ca.crt

Requirements: an OpenSSL 3.5+ `s_client` (for the `*` keyshare-prefix
syntax and the hybrid groups). The server needs no special setup — the
script only connects as a client. If your server uses a private CA, pass
--cafile; without it the handshake still completes (verification is not
fatal by default) and the negotiated group is still reported.

Tests:
  A  Deferred keyshare: the client supports X25519MLKEM768 but predicts
     ONLY a classical X25519 keyshare (`*X25519:X25519MLKEM768`).
     PASS if the negotiated group is X25519MLKEM768 (the server sent a
     HelloRetryRequest and forced the hybrid up). FAIL if it is X25519
     (silent classical fallback — the F-1 misconfiguration).
  B  Control: the client predicts the hybrid keyshare
     (`*X25519MLKEM768:X25519`). PASS if the negotiated group is
     X25519MLKEM768 (the server supports the hybrid at all). If B fails
     while A fails, the server does not support the hybrid at all.

Exit code: 0 if every test passes, 1 otherwise. Every check prints its
own PASS/FAIL line, so the output is self-explanatory.
"""
import argparse
import re
import subprocess
import sys

HRR_RANDOM = "cf21ad74e59a6111be1d8c021e65b891c2a211167abb8c5e079e09e2c8a8339c"


def run_client(openssl, host, port, groups, cafile, timeout=15):
    cmd = [openssl, "s_client", "-connect", "%s:%d" % (host, port),
           "-tls1_3", "-groups", groups, "-brief", "-msg"]
    if cafile:
        cmd += ["-CAfile", cafile]
    try:
        p = subprocess.run(cmd, input=b"", capture_output=True,
                           timeout=timeout)
        out = (p.stdout + p.stderr).decode("utf-8", "replace")
        return p.returncode, out
    except subprocess.TimeoutExpired as e:
        out = b"".join(x for x in [e.stdout, e.stderr] if x).decode(
            "utf-8", "replace")
        return "TIMEOUT", out + "\n[TIMEOUT after %.1fs]" % timeout


def negotiated_group(out):
    m = re.search(r"Negotiated TLS1\.3 group:\s*(\S+)", out)
    if m:
        return m.group(1)
    # Classical fallback: -brief prints "Peer Temp Key: X25519, ..." and
    # no "Negotiated TLS1.3 group" line.
    m = re.search(r"Peer Temp Key:\s*(X25519|secp256r1|secp384r1|X448)",
                  out)
    if m:
        return m.group(1)
    return None


def check(tag, got, want):
    ok = got == want
    print("%s: got=%r want=%r -> %s" % (tag, got, want,
                                        "PASS" if ok else "FAIL"))
    return ok


def main():
    ap = argparse.ArgumentParser(
        description="Check whether a TLS server enforces hybrid "
                    "X25519MLKEM768 when a client defers the hybrid keyshare.")
    ap.add_argument("--host", default="127.0.0.1")
    ap.add_argument("--port", type=int, default=443)
    ap.add_argument("--openssl", default="openssl",
                    help="path to an OpenSSL 3.5+ binary (default: openssl)")
    ap.add_argument("--cafile", default=None,
                    help="CA certificate for server verification (optional)")
    args = ap.parse_args()

    print("operator_check.py: %s:%d (openssl: %s)"
          % (args.host, args.port, args.openssl))
    ok = True

    # Test A: deferred hybrid keyshare.
    rc, out = run_client(args.openssl, args.host, args.port,
                         "*X25519:X25519MLKEM768", args.cafile)
    grp = negotiated_group(out)
    flat = "".join(out.split())
    hrr = HRR_RANDOM in flat
    ok &= check("A rc", rc, 0)
    ok &= check("A negotiated group (deferred keyshare)", grp,
                "X25519MLKEM768")
    ok &= check("A HRR seen", hrr, True)
    if grp == "X25519":
        print("A NOTE: server negotiated classical X25519 despite "
              "supporting the hybrid — flat-list misconfiguration (F-1).")

    # Test B: control — hybrid keyshare predicted.
    rc, out = run_client(args.openssl, args.host, args.port,
                         "*X25519MLKEM768:X25519", args.cafile)
    grp = negotiated_group(out)
    ok &= check("B rc", rc, 0)
    ok &= check("B negotiated group (hybrid keyshare predicted)", grp,
                "X25519MLKEM768")

    print("ALL PASS" if ok else "FAILURES PRESENT — see above")
    return 0 if ok else 1


if __name__ == "__main__":
    sys.exit(main())

05Findings memo — severity-ranked

Consolidated from the hybrid ML-KEM-768 TLS 1.3 assessment. Every finding was measured on OpenSSL 3.5.9 and wolfSSL 5.9.4-stable built from source, or is labelled specification-derived.

F-1HIGHmeasured

Flat server group list ignores server preference; deferred hybrid keyshare silently falls back to classical X25519

With a flat server list (X25519:X25519MLKEM768), the negotiated group follows the client’s order in both directions (D5: hybrid wins; D5b: classical wins). A client that supports the hybrid but predicts only a classical keyshare completes the handshake with classical X25519, no error, no HelloRetryRequest (R2). Relation to CVE-2026-2673: same downgrade class, but that CVE is specifically about the DEFAULT keyword (affects 3.5.0–3.5.5 / 3.6.0–3.6.1, fixed in 3.5.6/3.6.2); this build is 3.5.9, so F-1 is the residual flat-list behaviour, not a CVE reproduction.

Remediation (measured)Use the tuple syntax X25519MLKEM768/X25519; the server then sends an HRR (88-byte ServerHello, RFC 8446 magic random, key_share request 0x11ec) and the client negotiates the hybrid (R1). Operator test: python3 operator_check.py --host <server> --port 443 — test A must PASS. Proof: regression_hrr.py 9/9 PASS; operator check tuple ALL PASS, flat FAILS as expected.

F-2MEDIUMmeasured

wolfSSL 5.9.4 rejects standalone ML-KEM; OpenSSL 3.5.9 supports it

OpenSSL 3.5.9 negotiates standalone MLKEM768 (rc=0, TLS 1.3). wolfSSL 5.9.4’s example server refuses to start with --pqc ML_KEM_768: “invalid post-quantum KEM specified” (server.c:853). BoringSSL supports standalone ML-KEM-1024 only (specification-derived, IETF writeup); Go has no standalone ML-KEM TLS group (specification-derived).

RemediationUse hybrid groups (X25519MLKEM768) for interop; do not configure standalone ML-KEM unless every peer is confirmed to support it. Proof: case D6.

F-3MEDIUMmeasured

Legacy (pre-PQ) servers silently fall back to classical X25519

An OpenSSL 3.5.9 client against a genuine system OpenSSL 3.0.13 server negotiates X25519, rc=0, TLS 1.3, no error. The legacy server ignores the unknown group 0x11ec.

RemediationLog the negotiated group for every connection (SSL_get_negotiated_group() / the s_client “Negotiated TLS1.3 group” line) and alert when a connection that should be hybrid negotiates a classical group. “Client supports hybrid” does not imply “connection is hybrid”. Proof: case D3.

F-4LOWmeasured

TLS 1.2 is classical-only

A TLS 1.2-only client negotiates TLS 1.2 + ECDHE-ECDSA-AES256-GCM-SHA384 + X25519 (D4). ML-KEM groups are TLS 1.3 only (RFC 10024).

RemediationEnforce a TLS 1.3 minimum where post-quantum protection is required. Proof: case D4.

F-5LOW · informationalmeasured

Handshake latency is dominated by round trips

OpenSSL↔OpenSSL medians fit 2.5×RTT + ~10 ms at every condition (baseline 8.7 ms; 25 ms one-way → 137.0 ms; 100 ms → 512.9 ms; 250 ms → 1254.9 ms; 100% success, no timeouts). The 1,216-byte client key share adds no extra round trip on loopback. Limitation: MTU / fragmentation effects on real networks were not measured.

RemediationNone — informational. Proof: network trials (results.json).

F-6LOW · environmentmeasured

OpenSSL s_server closes connections when stdin is EOF

In a detached environment, s_server reads stdin in its accept loop and treats EOF as “done”, closing the connection before any handshake (strace: accept → read(0)=0 → DONE).

RemediationHold stdin open (pipe). Affects test harness automation, not TLS itself. Proof: strace log.

F-7LOW · environmentmeasured

wolfSSL example server: 1 connection by default; dies on a bare TCP probe

The example server serves 1 connection by default (-C raises it) and exits after a bare TCP probe’s SSL_accept fails with SOCKET_ERROR_E (-308).

Remediation-C 100; check readiness with ss -ltn, not a TCP connect. Affects the example server only, not the wolfSSL library. Proof: smoke tests.
